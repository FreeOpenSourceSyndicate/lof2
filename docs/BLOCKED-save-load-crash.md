The emulator cannot load a save and enter the play loop: the `play` golden is

## Symptom

Loading save slot 2 (`GAMES\GAME  2`) and entering the play loop jumps the CPU
to `0000:0000` and the run dies.

```
$ LOF_KEYAUTO=0x18,0x03 LOF_KEYGAP=8 LOF_CRASHDBG=1 \
  ./lof-native --dir game --headless --frames 1000 --shot /dev/null
[crash] cs:ip=0000:0000 ss:sp=4C92:B56A instr=10670008
```

Expected (recorded golden on `work/maintainer-town`):
`play c46f4fe9be490a1b77560a1e8136441e`
Actual: `b43512c10b9b22396b6b0dcdecf7a148` (the run never leaves the load).
The other six goldens (`boot`, `look`, `open`, `add`, `dism`, `erase`) match
exactly, so the crash is isolated to the save-load path.

## Reproducer

```sh
make                     # on origin/work/maintainer-town (needs LOF_KEYAUTO)
LOF_KEYAUTO=0x18,0x03 LOF_KEYGAP=8 LOF_CRASHDBG=1 \
  ./lof-native --dir game --headless --frames 1000 --shot /dev/null
```

`LOF_KEYAUTO=0x18,0x03` presses `O` (open) then Enter to pick save slot 2.
Note: **`LOF_KEYAUTO` only exists on `work/maintainer-town`** (added in
`ab42e4a`), not on `main`, so `main` cannot even drive the menu adaptively and
stops at `boot`.  Landing the adaptive-key feed on `main` is a prerequisite for
anyone else to reproduce this.

## Evidence gathered

1. **Last file access before the crash** (`LOF_READ=1`):

   ```
   [READ] file=game/GAMES/GAME  2 want=11834 got=11834 dest=5C92:0416
   [READ] file=game/GAMES/GAME  2 want=4     got=4     dest=4C92:B576
   [READ] file=GAMES/GAME  2     want=1296  got=1296  dest=4C92:B57C   <- last
   ```
   The save is read into `4C92:B57C`.  The crash stack is `ss:sp=4C92:B56A`, so
   the 1296-byte block lands **just above the stack pointer**.

2. **The faulting instruction** (last ~30 instructions via `LOF_RING=1`): control
   is in the dynamically-loaded segment `3A8D` and does `retf` (`CB`) from
   `3A8D:4900`, popping `ip=0000 cs=0000`.  Earlier in the same window the stack
   frame at `ss:B544`/`ss:B564` holds ASCII `' 5'`, `'05'`, `'0'` (`0x2020 0x2035
   0x3035 0x0030`) — i.e. **game data was written over the frame that held the
   return address**, so the `retf` reads zeros.

3. **`--vor` avoids the crash.**  Running `./lof-native --vor` (VOR first, then
   LOF, i.e. the real `START.BAT` order) with the same key feed does **not** hit
   `0000:0000`; it reaches the town screen (`ega\twn\twn00..05` are read) and
   ends at a normal `cs:ip=119D:17A6`.  This strongly suggests the
   copy-protection/residency state VOR installs (`lofx` in the INT 0xFA slot)
   affects the load path, and that the plain `LOF.EXE`-only start is the one that
   crashes.

4. **`LOF_PLANT_LOFX=1` alone does not fix it** (same `b43512c1…`), so it is not
   simply the `lofx` signature check.

## Hypothesis

The save-load routine allocates working memory and reads the save into it.  Under
the emulator the allocation lands at/just above the program's stack
(`4C92:B57C` vs `sp=4C92:B56A`), so the 1296-byte read overwrites the caller's
return-address frame; the eventual `retf` pops `0000:0000`.  The `AH=4A`
resize / `AH=48` bump allocator in `src/machine.cpp` (lines ~470–499) is the
prime suspect — it was already patched once for exactly this class of bug
("the game zeroes its return address"), and the save path allocates more/again
after the prologue shrink.  `--vor` changing the outcome points at the resident
memory layout differing between the two start paths.
